# Контракт серверного доступа v0.1

Статус: предложение для следующего шага. Публичный сервер этим документом не
включается и в этой задаче не разворачивается. `FixtureProvider` остаётся.

Учебный login PostgreSQL доказывает изоляцию локальной базы. Он не является
защитой публичного сервиса: пароль роли и строка подключения не заменяют
аутентификацию пользователя BOS.pro.

## Откуда сервер берёт личность

Проверенная личность появляется до обработчика запроса, на сервере.

Поле `user_id` в теле запроса не является аутентификацией. Контракт сценария
отклоняет это поле как `unknown_field` ещё до хранилища. То же относится к
`workspace_id` и роли, если клиент прислал их как заявление о правах, а не как
идентификатор уже выбранного сервером контекста.

Сервер сам решает, каким пользователем открыть runtime-подключение. В локальной
проверке это login-роль PostgreSQL: `session_user` должен совпадать с личностью,
которую сервер передал в `PostgresStore`. Параметр `bos.user_id` доступ не даёт.
Подключение superuser, владельца таблиц или роли с `BYPASSRLS` адаптер отклоняет
кодом `runtime_role_rejected`.

Ограничение текущей модели: один пользователь приложения = один PostgreSQL LOGIN
(`session_user`). Общий runtime-пул от имени одной роли с подстановкой разных
`userId` через GUC больше не подходит. Перед публичным сервером Дмитрию нужно
выбрать отображение проверенной сессии на DB-login (отдельные роли, или иной
согласованный механизм), и проверить, что пул не переносит чужой `session_user`
между запросами. Учебные login `alice`/`bob`/`viewer` — не публичная аутентификация.

## Как проверяются membership и роль

На каждой транзакции сервер передаёт только `workspace_id` выбранного контекста.
База сравнивает `session_user` с `bos.workspace_membership`.

- `owner` и `editor` могут создавать и изменять данные своего workspace.
- `viewer` может читать и не может писать.
- Нет строки membership — нет ни чтения, ни записи.
- Runtime-роль не выдаёт membership и не меняет роль.
- Составной внешний ключ не даёт связать task, run или artifact чужого workspace.

Клиент не выбирает роль. Роль читается из строки membership, которую создал
администратор базы.

## Операции

Публичного HTTP API ещё нет. Ниже — обязательное поведение серверного слоя,
когда он будет добавлен. Идентификатор пользователя в этих операциях берётся из
серверной сессии, не из JSON.

### Создание задачи

Сервер создаёт `task` в workspace, где у сессии есть роль `owner` или `editor`.
`project_id` должен принадлежать тому же workspace. Чужая пара
workspace/project отклоняется базой. Повтор с тем же идентификатором задачи не
создаёт вторую строку.

### Запуск задачи

Сервер вызывает `executePrepareDraft` от имени сессии и существующей задачи.
Ключ идемпотентности вместе с workspace и операцией определяет один запуск.
Повтор того же ключа и того же входа возвращает уже сохранённый запуск и не
создаёт второй. Тот же ключ с другим входом даёт конфликт и не перезаписывает
первый результат.

### Просмотр статуса, текста и отчёта

Сервер читает run, текущую версию текста и verification тем же
runtime-подключением. Чужой workspace не возвращает строку. В ответе нет строки
подключения, пароля и исходного `provided_text`, если клиент просил только
статус, текст черновика и отчёт.

### Сохранение новой версии

Сервер вызывает `reviseDraft`. Новая версия получает следующий номер под
блокировкой запуска. Две одновременные правки не занимают один номер и не
затирают друг друга. Записанная версия и её отчёт не обновляются. Изменение
текста снимает прежние привязки утверждений: пока новая проверка не сделана,
`quality_gate` остаётся `blocked`.

## Ошибки доступа, конфликты и идемпотентность

- Нет сессии или сессия не совпадает с login-ролью: запрос не выполняется.
  Учебный код адаптера — `runtime_role_rejected`.
- Сессия есть, membership нет: `workspace_access_denied` либо пустой результат
  чтения. Это не повод создать membership.
- `viewer` на запись: база не меняет строку.
- Повтор ключа с тем же входом: прежний `run_id`, отдельный успешный ответ
  повтора.
- Повтор ключа с другим входом: конфликт, первый запуск сохраняется.
- Ошибка записи после начала запуска откатывает частичный результат. В базе не
  остаётся успешный run без согласованных snapshot, артефакта и журнала.
- Отмена не снимается более поздним сохранением. Отказ поставщика, прерывание и
  восстановление остаются в статусе и в журнале.

## Журнал

Подотчётная запись — `bos.audit_event`. В ней есть шаг, исход и
`actor_user_id`, равный `session_user` на момент записи. Журнал не хранит пароль,
строку подключения и полный текст источника. `run_step` повторяет шаг без права
подменить инициатора из JSON.

## Границы доверия

- Браузер и другой клиент недоверенны. Их JSON не назначает личность, workspace
  или роль.
- Сервер доверен ровно в том, что он открывает runtime-подключение нужного
  пользователя и не подставляет superuser. Секрет администратора базы остаётся
  только у миграции и выдачи membership.
- База доверена в RLS, составных ключах, неизменяемости версий и журнале.
  Ошибка сервера не должна обходить эти ограничения правами superuser.
- Ответ модели и текст источника недоверенны. Они не меняют права и не пишутся
  в журнал целиком.
- `FixtureProvider` не проверяет живой URL и не тратит бюджет.

## Минимальный вариант аутентификации

Публичный способ входа ещё не выбран. Минимальный вариант, который можно
реализовать следующим шагом без публичного деплоя: серверная сессия.

Сервер после входа, способ которого выберет Дмитрий, выдаёт идентификатор
сессии в HttpOnly-cookie. Обработчик читает сессию из хранилища сессий на
сервере и только потом открывает runtime-подключение этого пользователя.
Идентификатор в cookie сам по себе не является `user_id` из тела запроса и не
передаётся в базу как параметр, которому база доверяет.

Пока выбор не сделан, публичный порт не открывается. Локальный учебный login
PostgreSQL остаётся проверкой RLS, а не входом в сервис.

## Решение, которое нужно от Дмитрия

Нужно выбрать способ публичной аутентификации: серверная сессия по схеме выше
или другой конкретный механизм. До этого выбора сервер наружу не публикуется.

Отдельно по-прежнему не выбраны endpoint и бюджет модели, хостинг и срок
хранения журнала. Роли `owner`, `editor` и `viewer` используются локально; их
замена тоже требует отдельного решения.

## Следующая реализация

Один локальный обработчик, без публичного сокета и без нового входа.

Он принимает личность только из заранее заданной серверной сессии тестового
процесса, открывает runtime-подключение этой login-роли и выполняет четыре
операции этого контракта: создать task, запустить `prepare_draft`, прочитать
статус, текст и отчёт, сохранить новую версию. Рядом проверяются отказ чужому
пользователю, конфликт идемпотентности и повтор того же ключа. `user_id` в теле
по-прежнему не аутентифицирует. Публичный сервер в этой реализации не
запускается.
