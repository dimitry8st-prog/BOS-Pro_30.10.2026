# Локальный серверный слой BOS.pro

Дата: 6 ноября 2026 года. База: `main` после объединения PR №2,
`46370d79bf9c9c6890e828ff14ac61c12e85974b`.

## Результат и границы

Добавлен обработчик внутри процесса: доверенная сессия → проверка запроса →
пул соответствующего DB LOGIN → RLS → сценарий → ограниченный ответ.
Новых зависимостей и миграций нет. Внешние действия и реальные модели не вызываются.

Это реализация раздела «Локальная реализация»
[контракта серверного доступа](SERVER_ACCESS_CONTRACT_V0_1.md).
HTTP-сервер, парольный вход, регистрация и публичная аутентификация не добавлены.
`LocalSessions.issue()` — доверенная операция серверного кода, не endpoint входа.
Нельзя выдавать сессию по `user_id`, присланному клиентом, без отдельной проверки входа.

## Сессии и права

`LocalSessions` выдаёт случайный 256-битный токен и хранит только его SHA-256.
Identity копируется при выдаче и чтении; подделанные, истёкшие и отозванные токены
отклоняются. Срок по умолчанию — 15 минут, максимум — сутки. Вместимость —
1024 активные сессии по умолчанию. Перезапуск процесса завершает все сессии.
Токены не выводятся в журнал.

Trusted bootstrap выбирает `userId`, `workspaceId` и отдельный пул пользователя.
Обработчик проверяет действующее membership через БД; выдача сессии сама по себе
не даёт членства. `session_user` должен совпадать с `userId`; superuser,
`BYPASSRLS` и владелец таблицы run отклоняются. Общий DB LOGIN на всех
пользователей по-прежнему несовместим с текущей моделью.

## Операции dispatch

| operation | Поля запроса кроме operation | Результат |
| --- | --- | --- |
| `create_task` | `task_id`, `project_id` | Создание в workspace сессии; повтор той же пары возвращает задачу; другая пара даёт конфликт |
| `prepare_draft` | `task_id`, `input` | Валидированный учебный сценарий существующей задачи; workspace подставляется сервером |
| `read_result` | `run_id` | Статус, текущий текст и отчёт проверки; task определяется по сохранённому run |
| `revise_draft` | `run_id`, `text` | Новая версия или unchanged; изменённый текст требует новой проверки |

`input` — прежний контракт prepare_draft **без** `workspace_id`. Поле
`project_id` выбирает ресурс, но не назначает права; оно должно совпадать с
проектом сохранённой задачи. Внешние `user_id`, роль, workspace и строка
подключения не принимаются. Неизвестные поля отклоняются. JSON-запрос ограничен
256 KiB, текст правки — 50 000 UTF-16 code units; ограничения сценария продолжают
проверяться отдельно.

Ответ имеет `{ status, body }`; это соглашение локального обработчика,
не существующий HTTP endpoint. Коды: 401 — отсутствующая сессия; 403 — запрет
доступа; 404 — ресурс не виден; 409 — конфликт; 400/413 — неверный запрос;
500 — внутренняя ошибка без SQL, DSN и секретов. Прочие пользовательские статусы
run, verification и publication учитываются отдельно от кода ответа.

Ответ явно выбирает разрешённые поля: run/status/quality_gate/cancel_requested,
publication/stop/costs, текущие artifact/text/hash/verification. Он не возвращает
snapshot, исходный `provided_text`, токен сессии или строку подключения.
Цитируемые фрагменты в verification являются частью отчёта и сохраняются.

`owner` и `editor` пишут, `viewer` читает. Проверки RLS выполняются на каждой
транзакции. Ключ идемпотентности остаётся в области workspace/operation;
попытка использовать его для другой задачи возвращает конфликт.

## Пример интеграции в доверенном тестовом процессе

```typescript
import { LocalSessions, LocalTaskApi } from '../src/index.js';
// alicePool создаётся сервером из серверного окружения, не из JSON клиента.
const sessions = new LocalSessions();
const api = new LocalTaskApi(sessions, userId => {
  if (userId !== 'alice') throw new Error('unmapped_identity');
  return alicePool;
}, process.cwd());
const token = sessions.issue({ userId: 'alice', workspaceId: 'ws_educational' });
const created = await api.dispatch(token, {
  operation: 'create_task', task_id: 'task_example', project_id: 'prj_educational',
});
// token не печатается и не включается в созданную задачу.
sessions.revoke(token);
```

Миграции, project и membership готовит администратор отдельно. API не получает
пул администратора и не выдаёт права пользователям.

## Проверки

Локально: Node.js 24.22.1 (в CI закреплена 24.12.0).

- `npm ci --ignore-scripts` — выполнено.
- `npm run check` — успешно.
- `npm test` — 16/16: прежние 11 проверок и 5 тестов сессий.
- `npm run test:postgres` без URL — PGlite, 3/3 включая подзадачу локального API.
  TCP и реальный парольный вход этот локальный прогон не проверяет.
- Native PostgreSQL 16 проверяет GitHub Actions с `BOS_TEST_DATABASE_URL`;
  итог нужно сверять с конкретным коммитом PR.

Интеграционные проверки выполняются и на PGlite, и в native-ветке существующего
набора: Alice/Bob/editor/viewer, отсутствие и подделка сессии, несоответствие
сессии DB LOGIN, чужой workspace, повтор задачи и конфликт проекта,
идемпотентный запуск и конфликт входов/другой задачи, чтение, версии и редактирование,
неизменность старой версии, отклонение неизвестных полей и выдача безопасного ответа.

Отдельная регрессия воспроизводит гонку: после чтения старого run другой запрос
создаёт заблокированную revision 2, затем первый запрос сохраняет тот же текст.
Ответ unchanged берёт run **внутри блокировки** и показывает `quality_gate=blocked`
вместе с revision 2, а не старый `open`.

## Дальше

Локальный loopback HTTP над этим обработчиком описан в
[LOCAL_HTTP_STAGE.md](LOCAL_HTTP_STAGE.md). Перед публичным входом нужно выбрать
реальный способ аутентификации и отображение подтверждённого пользователя на
DB LOGIN, затем cookie/CSRF при выбранной cookie-схеме, управление учётными
данными и проверки с браузером. Этот слой не подтверждает готовность публичного
сервиса. Запуск модели, бюджет, UI и деплой — отдельные этапы.
