# PostgreSQL: этап хранения и изоляции

Продолжение main после объединения PR №1 (`1137698`). Добавлены PostgreSQL RunStore,
миграция, транзакционные записи, идемпотентность и политики RLS. Существующий CLI
по умолчанию продолжает использовать файловое хранилище; PostgreSQL подключается
серверным кодом через `PostgresStore(pool, identity)`.

## Доверие и доступ

`identity` передаёт доверенный сервер после аутентификации: userId, workspaceId,
taskId. Веб-аутентификация и публичный API ещё не реализованы. Пользовательский JSON
или ответ модели не может быть источником identity. Секрет подключения к БД хранится
только на сервере. Runtime-роль может устанавливать контекст сессии: поэтому её
реквизиты нельзя выдавать клиентам, пользовательскому SQL или инструментам модели.

Администратор создаёт workspace, membership и выдаёт логину сервера членство в
`bos_runtime`. Runtime не может менять membership, удалять данные или переписывать
артефакты/отчёты. Viewer читает, editor/owner создаёт данные в своём workspace.
Проверка membership выполняется при каждой транзакции; RLS отдельно фильтрует строки.
Составные FK запрещают родительские связи между workspace. Права login-роли нужно
выдавать только на bos_runtime, без superuser/BYPASSRLS и владения таблицами.

## Установка схемы

Из корня проекта, в отдельной БД разработки, используя административный URL через
переменную окружения BOS_MIGRATION_DATABASE_URL:

```text
npm ci --ignore-scripts
npm run migrate:postgres
```

Миграция 001 транзакционная, имеет контрольную сумму и таблицу версий. Повтор не
пересоздаёт схему. Изменение применённой миграции вызывает checksum mismatch.
Роль `bos_runtime` создаётся на кластере, если её ещё нет. Повторная миграция
чистой базы в том же кластере не пытается создать роль заново. Автоматического
удаления схемы или данных нет.

Для отката приложения сохраните прежний адаптер и резервную копию данных. Этот
этап не удаляет и не переносит файлы прежнего dev-store. Схема откатывается только
отдельным административным решением; разрушительного down-скрипта нет.

## Использование адаптера

Создайте проект и task в разрешённом workspace. Task должен принадлежать проекту
из входного JSON; taskId передаётся отдельно серверным кодом. Затем:

```typescript
import { Pool } from 'pg';
import { PostgresStore, executePrepareDraft } from '../src/index.js';
const pool = new Pool({ connectionString: process.env.BOS_DATABASE_URL });
const store = new PostgresStore(pool, authenticatedIdentity);
const result = await executePrepareDraft(validatedInput, { store, root: process.cwd() });
```

Начальный учебный запуск сохраняется одной транзакцией: snapshot, run, журнал,
идемпотентность, артефакт и verification. Ошибка сохранения откатывает начальные
записи. Конкурентные одинаковые ключи сериализуются advisory lock и уникальным
ограничением; время ожидания блокировки ограничено. Изменение артефакта также
блокируется и сохраняется транзакционно. Старые версии не обновляются.

Длинные модельные вызовы внутри этой транзакции не поддержаны: перед реальными
API потребуется отдельный механизм lease/outbox/резервирования бюджета. При обрыве
соединения незавершённая транзакция откатывается БД; восстановление файловых PID
не используется для PostgreSQL. Это ещё не фоновые серверные workers.

## Проверки и ограничения

```text
npm run check
npm test
npm run test:postgres
```

Без BOS_TEST_DATABASE_URL последний тест запускает PostgreSQL/WASM (PGlite) на
диске: миграции, RLS под bos_runtime (не superuser и не BYPASSRLS), чужое чтение и
изменение, FK, viewer, откат, повторное открытие БД, версии и идемпотентность.
PGlite сериализует транзакции одного backend: это не доказательство TCP-конкуренции.

Для обычного PostgreSQL задайте BOS_TEST_DATABASE_URL административным подключением
к **чистой одноразовой тестовой БД** и выполните `npm run test:postgres`. Тест создаёт
схему и роль, не удаляет существующие данные. Повтор требует новой одноразовой среды.
GitHub Actions создаёт отдельный PostgreSQL 16 и исполняет тот же тест с настоящим
пулом соединений. Проверка миграционного runner и повторного применения в native
режиме также включена. Результат CI нужно проверять отдельно от локального прогона.

Локальная проверка на этой машине: `npm test` — 11 тестов, pass 11, fail 0,
duration_ms `3933.9126`. Нативный PostgreSQL `16.10` на `127.0.0.1:54329`, база
`bos_pr3_test` (отдельный учебный кластер `var/pg-test`, не служба на порту 5432):

```text
$env:BOS_TEST_DATABASE_URL = "postgres://postgres@127.0.0.1:54329/bos_pr3_test"
npm run test:postgres
```

Результат: `Native PostgreSQL transport tested`, pass 1, fail 0, duration_ms `1864.9213`.
Без этой переменной тот же тест на PGlite: pass 1, fail 0, duration_ms `10685.1546`.
Повтор на той же базе не запускался: тест наполняет её и не очищает данные.
Node в этой проверке — установленный локально; в `package.json` и CI закреплена `24.12.0`.

Не реализованы: публичная аутентификация, серверный API/UI, деплой, перенос прежних
данных, реальная модель и публикации. Новая БД не делает учебный генератор production.

- https://node-postgres.com/features/transactions
