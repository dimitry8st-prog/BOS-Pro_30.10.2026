# PostgreSQL: этап хранения и изоляции

Продолжение main после объединения PR №1 (`1137698`). Добавлены PostgreSQL RunStore,
миграция, транзакционные записи, идемпотентность и политики RLS. Существующий CLI
по умолчанию продолжает использовать файловое хранилище; PostgreSQL подключается
серверным кодом через `PostgresStore(pool, identity)`.

## Доверие и доступ

`identity` передаёт доверенный сервер после своей проверки: userId, workspaceId,
taskId. Веб-аутентификация и публичный API ещё не реализованы. Пользовательский JSON,
поле `user_id` и ответ модели не назначают личность. Секрет подключения хранится
только на сервере и не пишется в журнал.

Граница доверия: runtime-соединение может вызывать `set_config` для
`bos.workspace_id` (и теоретически `bos.user_id`). Эти GUC предполагают доверенный
сервер и **не** заменяют публичную аутентификацию. После миграции 002 доступ по
личности берётся из `session_user` (login-роль), а не из `bos.user_id`; подмена
`bos.user_id` чужие строки не открывает. `bos.workspace_id` по-прежнему задаёт
сервер в каждой транзакции. Адаптер сверяет `session_user` с `identity.userId` и
отклоняет superuser, `BYPASSRLS` и владельца таблиц кодом `runtime_role_rejected`.
Реквизиты runtime нельзя выдавать браузеру, пользовательскому SQL или модели.
Учебные login `alice`, `bob` и `viewer` проверяют локальную изоляцию. Это не вход
в публичный сервис.

Администратор применяет миграции, создаёт workspace, membership и task. Runtime
получает только членство в `bos_runtime`, без superuser, `BYPASSRLS` и владения
таблицами. Runtime не меняет membership. Viewer читает; owner и editor пишут в
своём workspace. Проверка membership выполняется при каждой транзакции. Составные
FK не связывают workspace между собой. Записанный артефакт и verification не
обновляются. Флаг отмены не снимается более поздним сохранением.

Подотчётный журнал — `bos.audit_event`: шаг и `actor_user_id` из `session_user`.
В него не попадают пароль, строка подключения и полный текст источника.

## Установка схемы

Из корня проекта, в отдельной БД разработки, используя административный URL через
переменную окружения BOS_MIGRATION_DATABASE_URL:

```text
npm ci --ignore-scripts
npm run migrate:postgres
```

Миграции 001 и 002 транзакционные. Контрольная сумма хранится в
`public.bos_schema_migration`. Повтор не пересоздаёт схему. Уже применённая 001
принимается и в исходном виде `516fc5a`, и в виде с идемпотентным созданием роли;
оба текста лежат в истории, неизвестная сумма по-прежнему останавливает запуск.
Проверка сумм не отключается. Новые правила личности и неизменяемости — миграция
002, она не переписывает применённую 001 и не удаляет строки. Роль `bos_runtime`
создаётся на кластере, если её ещё нет. Автоматического удаления схемы или данных
нет.

Для отката приложения сохраните прежний адаптер и резервную копию данных. Этот
этап не удаляет и не переносит файлы прежнего dev-store. Схема откатывается только
отдельным административным решением; разрушительного down-скрипта нет.

## Использование адаптера

Создайте проект и task в разрешённом workspace. Task должен принадлежать проекту
из входного JSON; taskId передаётся отдельно серверным кодом. Затем:

```typescript
import { Pool } from 'pg';
import { PostgresStore, executePrepareDraft } from '../src/index.js';
const pool = new Pool({ connectionString: process.env.BOS_DATABASE_URL });
const store = new PostgresStore(pool, authenticatedIdentity);
const result = await executePrepareDraft(validatedInput, { store, root: process.cwd() });
```

## Учебный запуск без правки исходников

Нужна отдельная локальная база `bos_educational`. Обычную и тестовую базы эта
команда не наполняет: без `BOS_EDUCATIONAL_DATABASE=1` и без имени
`bos_educational` на `127.0.0.1` или `localhost` сценарий останавливается.

Создайте пустую базу администратором кластера, например на учебном кластере
порта `54329`:

```text
createdb -h 127.0.0.1 -p 54329 -U postgres bos_educational
```

В этой оболочке задайте свои пароли runtime-ролей. Пароль — 12–128 символов из
латиницы, цифр, `_` и `-`. Не записывайте пароли в файлы репозитория и не
вставляйте их в журнал.

```text
BOS_EDUCATIONAL_DATABASE=1
BOS_MIGRATION_DATABASE_URL=postgres://postgres@127.0.0.1:54329/bos_educational
BOS_ALICE_DATABASE_URL=postgres://alice:<password>@127.0.0.1:54329/bos_educational
BOS_BOB_DATABASE_URL=postgres://bob:<password>@127.0.0.1:54329/bos_educational
npm run scenario:postgres
```

Административный URL применяет миграции и создаёт учебные workspace, membership,
проект и task. Сценарий выполняется login-ролью `alice`. Новое подключение `alice`
читает сохранённые черновик и отчёт. Login `bob` получает отказ на чужой
результат. Повтор команды возвращает тот же запуск. Очистка этой базы допустима
только как одноразовой учебной среды и этой командой не выполняется.

Начальный учебный запуск сохраняется одной транзакцией: snapshot, run, журнал,
идемпотентность, артефакт и verification. Ошибка сохранения откатывает начальные
записи. Конкурентные одинаковые ключи сериализуются advisory lock и уникальным
ограничением; время ожидания блокировки ограничено. Изменение артефакта также
блокируется и сохраняется транзакционно. Старые версии не обновляются.

Длинные модельные вызовы внутри этой транзакции не поддержаны: перед реальными
API потребуется отдельный механизм lease/outbox/резервирования бюджета. При обрыве
соединения незавершённая транзакция откатывается БД; восстановление файловых PID
не используется для PostgreSQL. Это ещё не фоновые серверные workers.

## Проверки и ограничения

```text
npm run check
npm test
npm run test:postgres
```

Без `BOS_TEST_DATABASE_URL` тест запускает PGlite: миграции, login-роли без
superuser и `BYPASSRLS`, отказ в подмене личности, чужое чтение, FK, viewer,
откат, версии, идемпотентность и обновление с прежней контрольной суммы 001.
PGlite сериализует транзакции одного backend. Это отдельный результат, не
замена TCP-проверки.

Для обычного PostgreSQL задайте `BOS_TEST_DATABASE_URL` административным
подключением к чистой одноразовой базе и выполните `npm run test:postgres`.
Тест создаёт login-роли `alice`, `bob` и `viewer`, подключается ими и не
удаляет данные этой базы. Повтор требует новой одноразовой базы. Если URL
указывает на `127.0.0.1` или `localhost` и база не называется `bos_upgrade_test`,
тест дополнительно создаёт и заменяет только одноразовую базу `bos_upgrade_test`,
чтобы проверить обновление с известной суммы 001. Неизвестная сумма оставляет
строки на месте.

GitHub Actions поднимает отдельный PostgreSQL 16 и выполняет тот же тест.
Результат CI для итогового commit нужно смотреть отдельно. Локальный прогон его
не заменяет.

Локальная проверка аудита 2026-11-01: `npm run check` — pass; `npm test` —
11/11 pass; `npm run test:postgres` без URL — PGlite 2/2 pass
(`Embedded PostgreSQL/PGlite tested; TCP transport not exercised`).
Нативный PostgreSQL 16 в одноразовом Docker на `127.0.0.1:55432`, чистая база
`bos_audit_run3`, административный URL только для миграции и seed; прикладные
операции — LOGIN `alice`/`bob`/`viewer`:

```text
$env:BOS_TEST_DATABASE_URL = "postgres://postgres:<password>@127.0.0.1:55432/bos_audit_run3"
npm run test:postgres
```

Результат: `Native PostgreSQL transport tested` и
`Native PostgreSQL upgrade from migration 001 tested`, pass 2, fail 0.
Повтор на той же базе не запускался: тест наполняет её и не очищает данные.
Отчёт аудита: [POSTGRES_AUDIT_2026-11-01.md](POSTGRES_AUDIT_2026-11-01.md).
Node — локальный; в `package.json` и CI закреплена `24.12.0`.

Не реализованы: публичная аутентификация, серверный API/UI, деплой, перенос прежних
данных, реальная модель и публикации. Новая БД не делает учебный генератор production.
