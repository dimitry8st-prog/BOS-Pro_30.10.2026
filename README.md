# BOS.pro

**Система управляемого выполнения задач с проверяемым результатом.**

Репозиторий: [BOS-Pro_30.10.2026](https://github.com/dimitry8st-prog/BOS-Pro_30.10.2026).
Статус: черновик концепции от 30 октября 2026 года. На ветке `scenario-contract-v0.1` есть учебный контракт v0.1, прогон `FixtureProvider` и локальный PostgreSQL для того же сценария. Это не готовое приложение, не публичная аутентификация и не решение, утверждённое владельцем.

BOS.pro помогает поставить задачу, выбрать проверяемый сценарий, получить результат
от ИИ и инструментов, проверить его и сохранить историю выполнения. Человек видит
исходные данные, результат, замечания, затраты и действия, требующие подтверждения.

Первый сценарий: подготовка публикации из проверенных источников с сохранением
черновика, проверкой ссылок и отдельным подтверждением публикации. Дальнейшие
направления — маркетинговые эксперименты и фоновые задачи создания видео.

## Первый результат разработки

Пользователь создаёт задачу и получает сохранённый черновик публикации, список
источников и отчёт проверки. Отдельный запуск имеет собственный статус, бюджет
и журнал. Наличие черновика не означает, что он опубликован.

## Учебный прогон v0.1

Команды выполняются из корня репозитория. Среда, в которой собран этот этап: Node.js `24.12.0`. Точные версии TypeScript и `@types/node` зафиксированы в `package-lock.json`.

```text
npm ci
npm run check
npm test
npm run scenario:fixture
```

`npm run scenario:fixture` записывает учебный запуск в каталог `var/dev-store`. Это файловое хранилище `development-only`: файлы переживают перезапуск процесса на этой машине. В нём нет проверки membership и RLS.

Код выхода `0` у команды `run` означает, что запуск сохранён со статусом `succeeded`. Одобрение текста смотрят в `verification`, публикацию — в `publication.status`. На этом этапе публикация остаётся `not_published`.

Повтор той же команды с тем же ключом возвращает тот же `run_id`. `FixtureProvider` не вызывает модель и не проверяет URL по сети. Прохождение теста не является проверкой реальной модели, живого сайта или production.

## Локальный PostgreSQL

Тот же сценарий записывается в отдельный учебный кластер. Используется установленный PostgreSQL `16.10`, каталог данных `var/pg-test`, адрес `127.0.0.1:54329`. Служба PostgreSQL на порту `5432` и её данные не используются. Облачный аккаунт не подключается.

Если программы `initdb` и `pg_ctl` лежат не в `C:\Program Files\PostgreSQL\16\bin`, перед командами задайте каталог `bin`:

```text
$env:PG_BIN = "C:\Program Files\PostgreSQL\16\bin"
```

Команды из корня репозитория:

```text
npm run db:bootstrap
npm run test:pg
npm run scenario:postgres
```

`db:bootstrap` создаёт кластер, если его ещё нет, роли `bos_owner`, `usr_educational` и `usr_other`, базу `bos_pro_test` и применяет миграции из `db/migrations`. `test:pg` удаляет и создаёт заново только базу `bos_pro_test` на этом кластере. Другие базы и пользовательские данные не очищаются.

Пароли `bos_owner_local_only`, `usr_educational_local_only` и `usr_other_local_only` действуют только в этом учебном кластере. Это не секреты публичного сервиса. Роль входа задаётся флагом `--actor`. Поле `user_id` из JSON не принимается.

Учебный адаптер проверяет membership и RLS ролью без `superuser` и без `BYPASSRLS`. Это локальная проверка изоляции, а не аутентификация публичного сервиса. Пока не выбраны модельный endpoint и бюджет, поставщик остаётся `FixtureProvider`.

Зафиксированные пакеты: `pg` `8.23.1`, `@types/pg` `8.23.1`, TypeScript `7.0.2`, `@types/node` `24.19.2`. Точные записи лежат в `package-lock.json`.
